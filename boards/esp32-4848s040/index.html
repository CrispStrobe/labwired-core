    GUITION ESP32-4848S040 C_I: functional display and touch model

    The configs/systems/esp32-4848s040.yaml system describes the common GUITION 480×480 capacitive-touch assembly with an ESP32-S3 N16R8 module, ST7701 RGB panel and GT911 touch controller. It adds a functional device path to the existing S3 instruction emulator. This board has guest-tested model behavior; it has not been validated against a physical S040 capture. The S3's older nine-register reset-state silicon anchor does not validate this display or touch behavior.

    What runs

    Firmware writes ordinary S3 LCD_CAM and GDMA registers. GDMA reads the guest's real descriptor chain and framebuffer through the system bus; LCD_CAM packs the bytes into sixteen-bit words, respects byte/bit ordering, and passes a complete active-area frame to a separate RGB panel interface. The panel receives its initialization through GPIO edges on the real 9-bit control stream. No Arduino, graphics-library or draw-pixel API is intercepted.

    The functional RGB subset supports:

    • Active width/height from LCD_CTRL and LCD_CTRL1, 16-bit RGB565 data, odd descriptor splits within a pixel, and LCD_USER byte/bit order.
    • Finite descriptor chains, cyclic chains with LCD_MISC.NEXT_FRAME_EN, owner checks, optional owner writeback, descriptor EOF, explicit LCD DMA stop, and reset/stop of the LCD transaction. Short, malformed and CPU-owned chains do not produce a completed frame. Failed RGB bus reads produce a descriptor error rather than invented pixel bytes.
    • A functional VSYNC event for each complete frame, interrupt enable/masking and write-one-to-clear acknowledgement. One-shot firmware may restart a frame from its VSYNC handler, as ESP-IDF 4.4.7 does.
    • ST7701 3-wire MSB-first control, extended command-bank selection, sleep in/out, display on/off, software reset, COLMOD storage, and the active-high backlight. The known type9 initialization selects COLMOD 0x60; this board still has sixteen RGB565 wires. The artifact represents those sixteen wires, without inventing two more DMA bits. The model accepts the known 0x50/0x60 modes.
    • GT911 product ID 911, a big-endian 16-bit register pointer, configuration storage, little-endian X/Y, one contact, ready/count at 0x814e, and the firmware's zero-write acknowledgement. Reports already read by the guest stay coherent through acknowledgement; later movement coalesces into the following report. Held-contact refresh uses simulation time (a modeled 10ms period), not the number of status reads.

    This is a functional frame model. VSYNC follows completed DMA active-area data; it is not a measured PCLK/porch deadline. Clock and sync timing registers round-trip, but the model does not generate RGB pad waveforms or enforce their GPIO matrix mux. Likewise, the existing S3 I2C attachment path associates the GT911 with I2C0; its recorded SDA/SCL route is not an electrical wrong-pin NACK test. It does not model LCD analog gamma/voltages, RGB888/8-bit output, tearing, cache-coherency faults, touch capacitance, gestures, five simultaneous contacts, GT911 interrupt/reset address strapping, or EEPROM configuration persistence. ST7701 hardware rotation is not inferred from another controller's MADCTL. Software-rotated guest framebuffers retain their raster order.

    The existing S3 CPU, ROM boot, flash MMU, octal PSRAM and other peripherals are reused. The new probe below is a focused bare ELF; it does not qualify arbitrary Arduino/LVGL/vendor merged-flash images, radio, native USB, SD, audio or relays.

    Board wiring and provenance

    This profile is the C_I capacitive-touch variant, not a claim that every board sold under the S040 name has interchangeable wiring.

    Internal signal GPIO
    ST7701 control CS / SCK / MOSI 39 / 48 / 47
    Backlight (active high) 38
    RGB DE / VSYNC / HSYNC / PCLK 18 / 17 / 16 / 21
    Red, low to high 11, 12, 13, 14, 0
    Green, low to high 8, 20, 3, 46, 9, 10
    Blue, low to high 4, 5, 6, 7, 15
    GT911 SDA / SCL, polling address 19 / 45, 0x5d

    The flat RGB565 D0…D15 order is [4,5,6,7,15,8,20,3,46,9,10,11,12,13,14,0]. These are internal device connections, not exposed expansion pins. The external H1 connector is a separate consumer-board/catalog concern. The common C_I profile does not wire touch IRQ or reset to the MCU.

    The public GPIO pad interface includes bank-1 H1 GPIO40/43/44, with bank-1 input/output, external drive/release, the existing pull-up/open-drain semantics, and probe/driver capture. It does not alias them onto GPIO8/11/12. The physical pad-number span ends at 48 and rejects the unbonded 22…25 holes; the 54 SVD register slots do not create extra physical pins. This extension does not qualify bank-1 GPIO interrupt delivery. Consumers must inspect direction and known drive; an unknown alternate-function drive is not a push-pull GPIO. The shared IO_MUX stores MCU_SEL without enforcing function arbitration, and the GPIO matrix's inversion bits are not applied. Consumers must refuse those unsupported configurations for attached circuits. GPIO40/43/44 require IO_MUX function 1 for GPIO; their function 0 routes are MTDO/U0TXD/U0RXD.

    Primary implementation references:

    • Arduino_GFX board definition at 6da54cb7, ESP32_4848S040_86BOX_GUITION. Its timing profile uses 12MHz PCLK, horizontal front/pulse/back 10/8/50, vertical 10/8/20. Other working firmware uses different porches; none is treated as a universal hardware constant.
    • ST7701 type9 initialization at the same commit, st7701_type9_init_operations, including COLMOD 0x60.
    • ESP-IDF 4.4.7 LCD register definitions, LCD low-level operations, and RGB driver.
    • Espressif GT911 driver at 67f41a16 for identification, contact packing, polling and acknowledgement.

    Consumer contract

    The standard display artifact has id display, kind framebuffer, format rgb565_be, and meta.w = meta.h = 480. Visibility also reflects display_on, sleeping, backlight_on and powered. frames_received counts complete accepted frames even while the backlight is off. A dark visible artifact is therefore distinguishable from firmware that never submitted a frame.

    Touch uses the existing generic stimulus interface, component id touch, channels x, y (0…479 pixels) and pressed (0 or 1). Send X/Y before pressed, preferably together in the existing atomic set_inputs call. Motion changes X/Y while pressed; release sets pressed to zero. No board-specific WASM API, renderer or hard-coded CPU hook is required.

    An external circuit may use the generic set_gpio_external(peripheral, pin, true/false/null) WASM API. null releases the external hold through the existing PadPort; it does not create a button or change the firmware's GPIO configuration. Numeric pins are validated before narrowing, unbonded pads fail, and accepted operations enter the replay journal so snapshots retain high/low/released behavior. This is a pad input capability; the consumer must still qualify direction, mux, pulls and electrical modes.

    Reproducible qualification

    tests/fixtures/esp32-4848s040/build_probe.py builds an original Xtensa ELF using only Python's standard library. The committed probe.elf is 18032 bytes, SHA-256 fc5563c16da88dc609c5ada36b17c72a611cc4998675d502572318c1657c419f. It uses no ROM/Arduino/host drawing calls: instructions initialize GPIO control, program LCD_CAM/GDMA, poll VSYNC, read and acknowledge nine GT911 bytes over the real I2C command-list registers, and resubmit the frame after touch input. Its first frame is four asymmetric color quadrants; a pressed contact paints pixel zero with the actual X coordinate read from the controller, and release makes that pixel red. UART0 emits S040 READY and S040 TOUCH.

    The probe uses SRAM1 only: code at 0x40378000, 480 row descriptors at 0x3fc90000, mailbox at 0x3fc91800, and three 960-byte row buffers at 0x3fc92000. Reused rows produce the full frame; the first row is independent so touch changes only pixel zero. The generator asserts non-overlap with the physical DRAM↔IRAM alias and avoids cache-owned SRAM0/SRAM2. A separate test reads a full RGB frame from the existing MMU-mapped octal PSRAM array. These are different pieces of evidence; the probe does not establish an Arduino PSRAM allocator or LVGL integration. See the fixture README for memory-map provenance and exact layout.

    python3 tests/fixtures/esp32-4848s040/build_probe.py
cargo test -p labwired-core --test esp32s3_rgb_s040 --test esp32s3_lcd_i80_pixels
cargo test -p labwired-core --test esp32s3_rgb_s040 --test esp32s3_lcd_i80_pixels --features event-scheduler
cargo test -p labwired-core --lib peripherals::components::gt911
cargo test -p labwired-wasm --lib gpio_external_tests
node tests/fixtures/esp32-4848s040/check_wasm.cjs /path/to/nodejs-engine

    The integration suite independently checks corner colors, row stride, odd DMA splits, byte swapping, cyclic updates, finite completion/VSYNC acknowledgement, software-rotated corner layouts, reset, sleep/backlight gating, unsupported 8-bit output, short/CPU-owned/malformed/stopped chains, real PSRAM reads and actual guest down/move/up redraw. Existing i80 tests remain unchanged.

    A source checkout or one local WASM build is not a qualified release pin. Consumers must wait for the existing immutable release process, its two independent builds, unchanged source/performance gates and retained-artifact qualification before adopting this board. Physical board validation remains pending even after those software checks pass.
